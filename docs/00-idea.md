# 00 — Original idea

I am working with a group of 3 B.Tech students on a 6–10 month research project in AI/LLM/Agent Security. We have finalized the research direction as:

SECURE RECOVERY / RECOVERABILITY OF MULTI-AGENT LLM SYSTEMS AFTER A SUCCESSFUL ATTACK.

The central idea is NOT to build another attack detector. We assume that an existing security mechanism/detector has already identified that an agent, execution, or event has been compromised. Our work begins AFTER detection.

The goal is:

Given a detected compromise in a multi-agent LLM workflow, determine exactly which information/state/work has actually become contaminated, determine how that contamination has propagated through the system, preserve unaffected legitimate work, and recover the workflow by invalidating and recomputing only the minimum necessary contaminated portion.

The key motivation is that current agent-security systems can often identify that an agent or trajectory is compromised, but agent-level compromise does not necessarily mean that everything produced by that agent is malicious or that every downstream agent is contaminated.

For example:

User
  ↓
Planner
  ↓
Researcher
  ↓
Coder
  ↓
Executor

Suppose the Researcher accesses a malicious webpage and produces several outputs:

Researcher:
  R1 = legitimate
  R2 = legitimate
  R3 = contaminated
  R4 = legitimate

The Researcher is then detected as compromised.

We should NOT simply label the entire Researcher agent, all its outputs, and every downstream agent as contaminated.

Instead, we want to determine:

1. Which specific event/output/state became contaminated?
2. What information caused that contamination?
3. Which later outputs actually depended on that contaminated information?
4. Which later outputs merely had access to the contaminated information but did not actually use it?
5. What is the smallest set of states/work that must be invalidated?
6. From which trusted checkpoint can we selectively recompute the affected work?
7. How can the system continue execution while preserving as much legitimate work as possible?

A critical distinction in our idea is between:

POTENTIAL DEPENDENCY
and
ACTUAL INFORMATION INFLUENCE.

For example:

Researcher:
R1 ✓
R2 ✓
R3 ✗ malicious
R4 ✓

Coder receives all four.

A simple chronological/dependency graph might say:

R1 ─┐
R2 ─┤
R3 ─┼──→ Coder
R4 ─┘

But this does NOT mean the Coder is contaminated.

If the Coder's final output actually used only R1, R2 and R4:

R1 ──→ Coder output
R2 ──→ Coder output
R4 ──→ Coder output
R3 ──X→ Coder output

then the Coder should remain CLEAN.

Therefore, merely being downstream of a compromised event is insufficient.

Our proposed system needs fine-grained provenance/influence tracking so that it can distinguish:

"the contaminated information was available to this agent"

from

"the contaminated information actually influenced this agent's state/output."

The architecture should therefore contain multiple related representations.

1. CALL / TOPOLOGY GRAPH

This represents the structural interaction between components:

User
 ↓
Planner
 ↓
Researcher
 ├── Web tool
 ├── Database
 └── Memory
 ↓
Coder
 ├── Code tool
 └── Memory
 ↓
Executor

This graph answers:

Who called whom?
Which agent interacted with which tool?
Which agents are downstream of another agent?

However, this graph alone cannot determine contamination.

2. EVENT / EXECUTION GRAPH

Every important operation in the agent workflow is represented as an event.

For example:

Event 101
Agent: Researcher
Input: user task
Tool: Web browser
Tool output: webpage content
LLM output: research result
Parent events: ...
Child events: ...

Event 110
Agent: Coder
Input: research results
Tool: code tool
Output: generated code
Parent: Event 101

The events can represent things such as:

- agent messages
- tool calls
- tool responses
- agent outputs
- plans
- decisions
- memory reads
- memory writes
- inter-agent communication
- derived outputs

3. PROVENANCE / INFORMATION-FLOW GRAPH

This is the most important part.

Each meaningful piece of information/state should have an identifier.

For example:

S1 = user instruction
S2 = trusted database result
S3 = malicious webpage content

Researcher produces:

R7

The provenance representation should capture which sources contributed to R7.

For example:

S1 ──→ R7
S2 ──→ R7
S3 ──→ R7

If S3 is identified as the malicious source and R7 incorporates its influence, R7 becomes contaminated.

Another Researcher output R8 might depend only on:

S1
S2

Therefore:

R8 = clean

even though it was generated by the same compromised Researcher.

The objective is therefore to reason at the level of individual states, outputs, messages, tool results, memory entries, decisions and derived results rather than treating an entire agent as one indivisible contaminated unit.

4. CONTAMINATION PROPAGATION

Once a compromised source/event is identified, the system should trace its influence through the execution/provenance structure.

For example:

Malicious source
      ↓
Researcher output R3
      ↓
Coder input
      ↓
Coder decision
      ↓
Generated code
      ↓
Executor action

But propagation must NOT simply follow chronological order.

If:

R3 = contaminated

and Coder received R3 but demonstrably did not use it, then:

R3 ✗
   ↓
   X
Coder ✓

The contamination should stop.

If the Coder actually incorporates R3 into its decision:

R3 ✗
   ↓
Coder decision ✗
   ↓
Generated code ✗
   ↓
Executor action ✗

then the contamination propagates.

Thus, the system attempts to identify the actual contaminated region rather than assuming that the entire downstream subgraph is contaminated.

5. RECOVERY

Once the contaminated region is identified, the system should NOT restart the entire multi-agent workflow.

Instead:

ATTACK
  ↓
DETECTION
  ↓
IDENTIFY CONTAMINATED SOURCE/EVENT
  ↓
TRACE INFORMATION PROVENANCE
  ↓
IDENTIFY ACTUALLY AFFECTED STATES
  ↓
PRESERVE CLEAN STATES
  ↓
INVALIDATE CONTAMINATED STATES
  ↓
FIND LAST TRUSTED CHECKPOINT
  ↓
SELECTIVELY RECOMPUTE AFFECTED WORK
  ↓
VERIFY RECOVERY
  ↓
CONTINUE WORKFLOW

For example:

Planner ✓
   ↓
Researcher
   ├── R1 ✓
   ├── R2 ✓
   ├── R3 ✗
   └── R4 ✓
          ↓
        Coder ✓
          ↓
       Executor ✓

If Coder never used R3, the recovery may only need to remove/recompute R3.

But if:

R3 ✗
 ↓
Coder decision ✗
 ↓
Code ✗
 ↓
Executor action ✗

then these affected states need to be invalidated and selectively replayed from an appropriate trusted checkpoint.

The key objective is:

RECOVER THE WORKFLOW, NOT NECESSARILY THE ENTIRE AGENT.

An agent itself may not be permanently malicious. A particular message, memory entry, tool response, decision, plan, or generated output may be contaminated.

6. RECOVERY UNITS

The system should treat the following as possible recoverable units:

- messages
- tool responses
- tool calls
- memory entries
- plans
- decisions
- agent states
- inter-agent outputs
- derived outputs
- execution results

The system should determine the minimum set of these units that must be invalidated and recomputed.

7. CHECKPOINTS AND STORAGE

The system requires enough execution history to perform recovery, but the goal is NOT to permanently duplicate every token or every intermediate computation.

The conceptual design is:

TRACE STORE

├── Lightweight provenance metadata
│     ├── event ID
│     ├── parent IDs
│     ├── agent ID
│     ├── input/output references
│     ├── tool ID
│     └── memory references
│
├── Selected checkpoints
│
└── Required state/content

The important research problem is therefore not simply "store everything."

It is:

Given limited execution history/provenance information, determine the minimum safe recovery set while preserving unaffected work.

Storage overhead is itself an important consideration because fine-grained recovery requires additional tracing information.

8. EXAMPLE

Consider:

User
 ↓
Planner
 ↓
Researcher
 ↓
Coder
 ↓
Executor

Researcher reads:

A = trusted documentation
B = trusted database
C = malicious webpage

Researcher produces:

R1 = based on A + B
R2 = based on A
R3 = based on C
R4 = based on B

Suppose R3 is contaminated.

Coder receives:

R1, R2, R3, R4

but generates code using only:

R1, R2, R4.

Then:

R3 = contaminated
Coder output = clean
Executor output = clean

No unnecessary recovery should occur.

Now consider another run where the Coder uses R3:

R3 = contaminated
   ↓
Coder decision = contaminated
   ↓
Generated code = contaminated
   ↓
Executor action = contaminated

The recovery mechanism should identify this affected chain and selectively recompute it while retaining independent clean work.

9. CORE RESEARCH PROBLEM

The research problem can therefore be expressed as:

"How can a multi-agent LLM system recover from a detected security compromise by identifying the fine-grained states and outputs actually influenced by contaminated information, distinguishing actual information flow from mere exposure, and selectively recomputing only the affected portion of the workflow while preserving legitimate work?"

The proposed system is therefore composed conceptually of:

Existing Attack Detector
        ↓
Compromised Agent/Event
        ↓
Execution Tracing
        ↓
Call/Topology Graph
        +
Event Graph
        +
Information Provenance
        ↓
Fine-Grained Contamination Analysis
        ↓
Contaminated Region
        ↓
Recovery Planner
        ↓
Selective Invalidation
        ↓
Selective Replay/Recomputation
        ↓
Recovery Verification
        ↓
Continue Workflow

The main conceptual novelty we are investigating is the combination of:

fine-grained contamination attribution
+
actual information-flow/provenance analysis
+
minimal safe recovery
+
selective replay

for security-induced failures in multi-agent LLM workflows.

The system should prioritize SECURITY FIRST: if it cannot confidently establish that a state is unaffected, it should conservatively invalidate/recompute it rather than preserve potentially contaminated work.

The final objective is not simply to detect that an agent was attacked. It is to answer:

"Exactly what work was contaminated, where did that contamination actually propagate, what legitimate work can safely be preserved, and what is the minimum amount of work that must be recomputed to safely continue the task?"
